## [0.3.2] - 2026-10-10

### Changed
- **Each commit is tested once** ([docs/RELEASES.md](docs/RELEASES.md)). `ci.yml` runs on pull requests and pushes to `develop`, and `release.yml` calls it (`workflow_call`, with `build-pwa: false`) on each release candidate's commit: the pre-release `vx.y.z-rc.N` is created only after CI passed. It no longer runs on pushes to `main`, `release/**` and `hotfix/**`, and on pull requests into `main` its test jobs are skipped, since their head is the already tested candidate.
- **The pull request to `main` and the back-merge pull requests are opened by the GitHub App te-tengo-release-bot** (`RELEASE_APP_ID`, `RELEASE_APP_PRIVATE_KEY`), so their checks run; nothing falls back to `GITHUB_TOKEN`. The release pull request's description names the pipeline run with its attempt, so each new candidate edits it and runs `release-gate` again.
- **Tag only what is live.** `produccion.yml` tags `vx.y.z` (`Tag vX.Y.Z and GitHub Release`) only when no produccion job failed or was rejected and at least one was published; with every channel switched off there is no tag and no back-merge, and the summary says so. The back-merge is its own job, `Back-merge into develop`, with auto-merge (merge commit) when the repository allows it, and after a hotfix it also opens `main` → newer open `release/*` branches.
- `candidata.sh buscar` returns the newest **approved** candidate built from the tree (staging `passed` or `skipped`, tag on a commit with that tree), so an older approved rc wins over a newer pending one with the same tree; produccion and `release-gate` share it.
- **Deploy secrets are checked where they are used.** `Version and configuration` checks only the signing secrets and the build variables; the staging, produccion and rollback jobs check their own Cloudflare, Google Play and App Store Connect secrets as their first step, with an error naming the missing one.
- Every secret is read by the step that uses it, never by a whole job. Workflows grant nothing by default, each job declares its permissions, and no checkout keeps the token.
- Rollback runs only from `main`.

### Added
- **`ci-ok`**, the single required CI check: it fails unless every CI job passed (on pull requests into `main`, unless the head is `release/x.y.z` or `hotfix/x.y.z`).
- **`release-gate`** (`release-gate.yml`, required on `main`): a release or hotfix pull request may be merged only when merging puts into `main` exactly the tree of a candidate that passed staging, the candidate produccion then publishes.
- **`pr-title`** (`pr-title.yml`): pull request titles must be Conventional Commits.
- **SBOM and attestations of each release candidate.** `te-tengo-sbom.spdx.json` (Dart and Swift packages) is an asset of the candidate and of the final release, and every file gets a build provenance attestation, plus an SBOM attestation for the APK, PWA, AAB and IPA (`gh attestation verify <file> --repo Te-Tengo-Tech/te-tengo-mobile-flutter`).
- Dependabot also updates the Android Gradle build (`/android`).
- A rollback rehearsal procedure in [docs/RELEASES.md](docs/RELEASES.md#rollback-rehearsal).
- A weekly `branch-cleanup.yml` (Mondays 04:00 UTC, or by hand with a dry run) deletes branches merged 7+ days ago and unmerged branches with no commits for 30+ days; it never touches `main`, `develop`, `release/*`, `hotfix/*`, branches with an open pull request or pull requests labelled `do-not-delete`, and `BRANCH_CLEANUP_ENABLED=false` turns it off.

### Removed
- The cross-repository mode of `build-apk.yml` (`ref` input and `MOBILE_REPO_TOKEN`): the landing no longer builds the app.
- The AAB build on pull requests, and the `Release` run on pull requests into `main`.

### Security
- **Signing secrets never reach pull request code.** Pull requests no longer call `build-apk.yml` with `secrets: inherit`: the `APK build check` passes no secrets and signs with the debug key. The signing jobs (`Version and configuration`, `APK`, `AAB`, `IPA`) run in the environment `firma` on pushes to `release/*` and `hotfix/*` only, and `APK`/`AAB` fail instead of debug-signing when a publishing channel is on and the release key is missing.
- Deploy tokens move to the environments `staging` and `produccion`.
- Every action is pinned by full commit SHA.

## [0.3.1] - 2026-10-09
### Fixed
- **Event clip controls.** The clip bar now has play and pause, «Volver a ver el clip» at the end, −5 s and +5 s, a progress track that can be tapped or dragged (and moved 5 s at a time by screen readers, «Avance del clip»), the time, and full screen; every target is at least 48 dp. While the player does not know the duration yet, the clip still plays and shows the nominal 0:12, but cannot be sought. Play no longer rewinds to the start when the duration is unknown, and the video is laid out at its own size: the `AspectRatio` inside a `FittedBox` failed its layout («RenderAspectRatio has unbounded constraints»).
- **Expired clip URL.** The pre-signed URL of `GET /api/alertas/{id}/clip` lasts 5 minutes and was never renewed, so a clip opened later or left paused failed. The player (`ReproduccionClip`) now asks for a new URL when the player fails, when it does not open within 10 s or plays without moving for 8 s (on the web an expired URL can leave `video_player_web_hls` waiting without an error), before a command once `expiraEn` is less than 30 s away, and while playing just before `expiraEn`. It resumes at the same position, playing if it was, with the old video on screen until the new one is ready. Only `404 CLIP_NO_DISPONIBLE`, `410 CLIP_ELIMINADO` or three failures in a row show the existing «Clip no disponible» or «La grabación ya no está disponible». On the web the clip is muted (it has no sound), so it may resume outside a tap.
- **Full screen for the clip.** Android and iOS open a full-screen view with the same controls, landscape allowed and immersive system bars, and restore the orientation and the bars when it closes (its button, back, or a gesture). The PWA puts the page in the browser's full screen (Fullscreen API) with the same view; in Safari on iPhone, which has no Fullscreen API, the video element's own full screen (`webkitEnterFullscreen`, with the system controls) is used. See `docs/WEB_PWA.md`.
- **Two push registrations at once.** `registrar()` was called from four places (start, session change, resume, «Activar notificaciones») without waiting for the one under way, so a phone could ask FCM for a token twice and register two tokens 23 ms apart. Only one registration runs now; calls made meanwhile wait for a single one that runs right after it and get its result. A token the phone no longer uses is deleted from the backend (`DELETE /api/dispositivos/{tokenPush}`).
- **Registration on every start and return.** `POST /api/dispositivos` is sent on every start and every return to the foreground, so the backend records when the phone was last seen (`vistoEn`) and a token FCM changed silently (on the web `onTokenRefresh` never fires) is registered. Other session changes register at most once every 30 s.
- **Tokens the push service dropped.** The app keeps the `id` of `201 Dispositivo` and asks `GET /api/dispositivos/{id}` before registering again; when the backend answers `activo: false`, it deletes its FCM token (`deleteToken()`), gets a new one and registers that. Contract §7.
- **Errors were swallowed.** A Firebase error while getting the token (other than iOS still waiting for APNs) or a failed registration is no longer ignored: Inicio and Notificaciones say «Este celular no recibe las alertas» with «Activar notificaciones», which registers again.
- **«Notificaciones activadas» from the permission alone.** Notificaciones and the confirmation toast said the alerts would arrive with the app closed once the browser or system allowed notifications, even when the backend had no active device. They now wait until the backend has this phone, and when `GET /api/hogar` answers `dispositivosActivos: 0` Inicio and Notificaciones say «Nadie de la familia recibe las alertas». New copy in `docs/BLOCKERS.md`.
- **A lost push left the alert unseen with the app open.** Inicio asks for the active alert every 20 s while it is visible and the app is in the foreground, so the tab shell opens a new alert whose push never arrived.
- **«Seguimos reintentando» when nothing retried.** The alert screen and its timeline said the notification was being sent again whenever `notificadaEn` was empty. They now follow `estadoAviso` (contract §5): «Seguimos reintentando el envío» only with `REINTENTANDO`; with `NO_ENTREGADO` the alert says it did not arrive as a notification and the timeline «La notificación no se pudo entregar»; nothing while it is `ENVIANDO`.
- **Android channel and iOS foreground.** `MainActivity` creates the notification channel `alertas_caida` («Alertas», high importance, public on the lock screen) that the backend sends alert pushes to, and the manifest makes it the default FCM channel, so a fall is a heads-up notification with sound. On iOS a push that arrives with the app open also shows the system banner and plays its sound (`setForegroundNotificationPresentationOptions`).
- **PWA notifications while a window is visible.** The Firebase SDK shows nothing when a window of the app is visible, so a fall arriving while the PWA was open in the background or another tab never reached the screen. The service worker now shows every push itself, with the backend's `tag` (the alert's id) so a later notice of the same alert replaces the earlier one and Firebase's own copy replaces it without alerting twice; urgent notices stay until dismissed (`requireInteraction`). See `docs/WEB_PWA.md`.

## [0.3.0] - 2026-10-09
### Added
- **Live view over WebRTC (WHEP), with LL-HLS as the fallback.** When the session response carries `urlWebrtc`, the app plays the stream over WebRTC first, well under a second behind instead of the 2–5 s of LL-HLS: `flutter_webrtc` on Android, iOS and the web (the browser's `RTCPeerConnection`), receive-only video, one WHEP `POST` with all the viewer's candidates, no TURN, the viewer token only in the `token` query parameter (contract §4), and the WHEP session deleted when the view closes. While the camera is not publishing yet (`404`) the offer is sent again every 0.5 s, for up to 8 s from the session's start (`esperaPublicacionWebrtc`). A rejected offer, an answer slower than 4 s, no first frame within 4 s of the answer, a broken peer connection or 3 s without frames switch the same session to LL-HLS, with its existing start-up and watchdogs (after a break mid-stream, LL-HLS has 10 s, `esperaRescateHls`, to show a frame); a new session tries WebRTC again. Without `urlWebrtc` (an older API, or WebRTC turned off) nothing changes. Contract: `docs/API_CONTRACT.md` §4.
- **`preparar`:** the camera detail and an open alert send `POST /api/vista-en-vivo/preparar {camaraId}` once when they open, so the household agent gets ready before «Ver en vivo» is tapped; no image leaves the home until a session opens. Errors (an older API or agent, a paused camera) are ignored.

## [0.2.1] - 2026-10-09
### Fixed
- **Live view that never started in the PWA when the camera began publishing after the session opened.** Until the camera publishes, MediaMTX answers `404` for the playlist; `video_player_web_hls` 1.3.0 swallows hls.js's fatal error for it, so the player's `initialize()` never completed and no retry ran until the 20 s watchdog ended the session. The app now asks for the playlist every 2 s and creates the player only once it is served, and each start attempt is limited to 6 s (`esperaInicio`) before a new player is tried, within the 20 s the screen waits for the first frame. Android and iOS use the same start-up.
- **Frozen live view in Chrome and Edge 142+.** Chromium now reports native HLS, so the plugin used Chromium's new built-in player, which fails on MediaMTX's LL-HLS (`DEMUXER_ERROR_COULD_NOT_PARSE`) and left the hls.js fallback paused on the first frame. `web/index.html` reports no native HLS in Chromium browsers once hls.js is loaded, so they play with hls.js as intended; Safari keeps its own player. See `docs/WEB_PWA.md`.

## [0.2.0] - 2026-10-09
### Changed
- **Release pipeline: release candidates, staging from the release branch, produccion from `main`, tag at the end** ([docs/RELEASES.md](docs/RELEASES.md)). It replaces `release-android.yml`, `release-ios.yml`, `etiquetar.yml` and the landing's `publicar.yml`.
  - A push to `release/x.y.z` or `hotfix/x.y.z` (`release.yml`) builds once: signed APK, PWA, AAB with `ENABLE_PLAY_STORE`, IPA with `ENABLE_IOS`. It stores the files as the GitHub pre-release `vx.y.z-rc.N`, whose notes record the commit, git tree, build number, SHA-256 of every asset (`SHA256SUMS`) and the channels that were on. After an approval it deploys that candidate to **staging** (environment `staging`, `ENABLE_STAGING`: PWA alias `https://staging.te-tengo-app.pages.dev`, APK R2 `staging/te-tengo.apk`), then opens or updates the pull request `release: x.y.z` to `main`.
  - The build number (versionCode, CFBundleVersion, PWA `version.json`) is computed for each candidate: one more than the highest recorded by any candidate, never below the `+N` of `pubspec.yaml`. It is passed with `--build-number`, so no manual bump is needed.
  - A push to `main` (`produccion.yml`) finds the candidate whose git tree equals `main`'s and that passed staging, and fails otherwise («main differs from the tested candidate»). After an approval on `produccion` it publishes the same files without rebuilding, after checking their SHA-256: PWA `https://app.tetengo.reqsai.tech`, APK R2 `te-tengo.apk`, the same AAB to the Google Play internal track, the same IPA to TestFlight.
  - Only if every channel that is on succeeds, `produccion.yml` creates the GitHub Release `vx.y.z` with the same assets and the `CHANGELOG.md` section, and opens the back-merge pull request `main` → `develop`.
  - A missing secret or variable of a channel that is on fails the run before the builds or the approval; the run summary shows the plan and why each skipped job is skipped.
- The PWA build is the reusable `build-web.yml`, shared by `CI` and `release.yml`, with optional `build_name` and `build_number` inputs; the Cloudflare Pages files (`_headers`, `robots.txt`) moved here from the landing, to `deploy/pwa/`.
- `CI` also runs on pushes to `release/*` and `hotfix/*`, so the release pull request carries the required checks.
- The Play release status comes from the optional variable `PLAY_RELEASE_STATUS` (`completed` by default) instead of a manual-run input.
- `Release Android` is switched by the organization variable `ENABLE_PLAY_STORE` instead of by the presence of its secrets. On a push to `main` the AAB is built and uploaded to the internal track, after approval, only when the variable is `true`. A missing `PLAY_SERVICE_ACCOUNT_JSON`, release key, `GOOGLE_SERVICES_JSON` or `TT_API_URL` then fails the run with an error. `r0adkll/upload-google-play` is pinned by commit SHA, and the package name is read from `applicationId`.
- `notificar-landing.yml` sends the `publicar-movil` dispatch only when `ENABLE_PWA` or `ENABLE_APK` is `true`.
- Release flow: a release merged into `main` is published after an approval on the `produccion` environment (required reviewers, `main` only). The new `notificar-landing.yml` sends `repository_dispatch` `publicar-movil` with `{ref, version}` to `te-tengo-landing-astro` when `CI` succeeds on a push to `main` (needs the `DISPATCH_TOKEN` secret; a notice without it). `release-android.yml` runs on push to `main` instead of `mobile-v*` tags and uploads to Google Play in a separate `Upload to Google Play (internal)` job in `produccion`, after the AAB is built.
- The PWA is served at the root of its own origin, `https://app.tetengo.reqsai.tech/`, instead of `/app/` of the landing: the CI `Web (PWA)` job builds with base href `/`, and `docs/WEB_PWA.md`, `docs/FIREBASE.md` and `docs/BLOCKERS.md` give the new e-mail link base (`TT_ENLACE_BASE=https://app.tetengo.reqsai.tech/#`), CORS and HLS origin, API key referrer and service worker scope (`/`).

### Added
- `rollback.yml` (manual, input `version`): after an approval on `produccion`, republishes the PWA (and, when asked, the APK) of an earlier GitHub Release `vx.y.z` from its stored assets, checked against its `SHA256SUMS`; no build. `docs/RELEASES.md` explains the limits for the APK and the stores and when the API database must be restored.
- `.github/scripts/candidata.sh`: numbers, creates, finds and downloads (with SHA-256 checks) the release candidates, and creates the final release.
- **Store releases with organization-level switches** ([docs/RELEASES.md](docs/RELEASES.md)): every release channel has an on/off organization variable, `ENABLE_PWA`, `ENABLE_APK`, `ENABLE_PLAY_STORE` and `ENABLE_IOS`, on only when `true`. `docs/RELEASES.md` gives the channels, the job graph for each combination, the secrets and variables, the costs (Google Play US$25 once, Apple Developer Program 99 USD per year) and the steps to turn each channel on.
- `Release iOS` (`release-ios.yml`), run when `ENABLE_IOS` is `true` on a push to `main` or by hand:
  - `Build IPA` on `macos-26` with Xcode 26.6 checks every secret and the provisioning profile. It signs manually with the distribution certificate in a temporary keychain, adds `GoogleService-Info.plist` from `GOOGLE_SERVICE_INFO_PLIST`, and runs `flutter build ipa --export-options-plist` with `TT_API_URL` and the `pubspec.yaml` version. It verifies the IPA's signature and entitlements and keeps it as an artifact.
  - `Upload to TestFlight` waits for approval on `produccion`, then uploads through the App Store Connect API (`apple-actions/upload-testflight-build`, pinned by SHA).
- **Web app (PWA) for iPhones without the App Store build:** the web platform with the brand manifest (`Te Tengo`, `#4A2A85`, standalone, relative scope), icons rendered from `assets/icono/` (192/512, maskable, apple-touch-icon) and iOS meta tags; one service worker (`firebase-messaging-sw.js`, network-first offline cache and FCM Web Push) instead of Flutter's deprecated one; Firebase web config and VAPID key from `--dart-define` (`TT_FIREBASE_WEB_*`, `TT_FCM_VAPID_KEY`); token registered as `plataforma: WEB`; permission asked only from «Activar notificaciones»; tapped notifications open their screen; the «Agrega Te Tengo a tu pantalla de inicio» notice and guide on iPhone browser tabs; hash URLs so the e-mail links open under `/app/`; `localStorage` cache, browser downloads, `tel:` links and hls.js live view in the browser. CI job `Web (PWA)` builds `--base-href /app/` and uploads `te-tengo-web`. Guide: `docs/WEB_PWA.md`.
- Sideload distribution: the reusable `Build APK` workflow (`build-apk.yml`, `workflow_call`) builds the universal release APK `te-tengo.apk`, signed with the same release key as the AAB, verifies it with `apksigner` and keeps it with its SHA-256 as a `te-tengo-apk` artifact. `Release Android` calls it, and so does the landing's publish workflow, which uploads the APK to Cloudflare R2. `TT_API_URL` is accepted as a variable or a secret. `docs/RELEASE_ANDROID.md` explains how testers install it from the landing page («Instalar apps desconocidas») and how updates work.
- Android release pipeline: release signing with the upload key from `android/key.properties` (template `key.properties.example`; debug key when absent), and the `Release Android` workflow, which builds the release AAB from the `pubspec.yaml` version and uploads it to Google Play's internal track on `mobile-v*` tags or manual runs; it is inert without its secrets. Setup, Play App Signing, testing rules and store policy forms: `docs/RELEASE_ANDROID.md`.
- CI: separate format/analyze and test jobs with lcov coverage artifact and summary, superseded runs cancelled; weekly OSV-Scanner scan of `pubspec.lock`; Dependabot, CODEOWNERS, issue and pull request templates, security policy and code of conduct.
